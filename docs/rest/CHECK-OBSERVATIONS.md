# Check observations

Run `npm run check:preflight` with Node.js 26.13.1 from `.nvmrc` and `TEST_DATABASE_URL` set to a disposable PostgreSQL 16 database. The preflight verifies connectivity, the server version and schema permissions in a rolled-back transaction. It never prints the connection string. Focused `npm test -- test/<file>.test.ts` remains usable without PostgreSQL; skipped integration suites in that command do not establish release readiness.

Install the pinned browser once with `npx playwright install --only-shell chromium`; Linux CI uses `npx playwright install --with-deps --only-shell chromium`. The required browser suite drives Chromium's virtual authenticator, parses its actual credential-creation response and verifies discoverable assertions, including missing UV and incorrect challenge/origin. Its small report and screenshot are under `.generated/wallet-observations/browser-required/`. It persists no credential, assertion or private key. This checks the browser producer and server boundaries, not shared-wallet UI or physical-device compatibility. Browser absence fails the required suite instead of silently skipping it.

For the separate physical Mac observation, run `npm run wallet:device-probe` and open its printed `http://localhost:<port>` URL in the browser being tested. This temporary, loopback-only probe uses the `localhost` RP, bounded in-memory state and a 15-minute lifetime. It creates a test discoverable credential and verifies a fresh assertion; it creates no Center account, login or payment. A credential can remain in the device's passkey store afterward. Record the actual device/browser, prompt and final server verification result. The probe's required HTTP-boundary and virtual-authenticator browser tests are automated evidence only; the latter writes a report and screenshot under `.generated/wallet-observations/device-probe/`. Do not treat those artifacts as physical-device results.

The local Mac probe has passed in user-confirmed Safari and instrumented installed Chrome with real passkey prompts. Chrome initially returned a different saved credential; in-memory correlation identified the mismatch, and selecting the newly created credential passed. Sanitized physical evidence is kept separately in `physical-summary.json` and `physical-chrome-events.ndjson`. The user has a Mac, iPhone and iPad; this Mac browser observation does not cover iPhone/iPad Safari, cross-device sync, production RP or native handoff. Installed versions and remaining device requirements are recorded in [the implementation record](CENTER-WALLET-IMPLEMENTATION.md#gate-a-status).

`npm run check` runs that preflight, the existing pinned execution checks, passkey compatibility checks, wallet-client checks, typechecking, every service test and the build. Its service JSON report must contain every required database and execution suite, with nonzero tests and zero failures, skips or todos. A missing report fails the check, even if the child process exits successfully.

Each command prints an observation path under ignored `.generated/checks/<run-id>/`. `summary.json` records the revision, whether the working tree was dirty, start/end source fingerprints and times, the result, per-step exit status, per-suite test counts and relative log paths. Source fingerprints hash actual tracked and non-ignored untracked bytes and modes, including missing and newly staged paths; `dirty` compares those bytes and the index directly to HEAD blobs. Assume-unchanged, skip-worktree and clean filters cannot hide source differences. Symlinks contribute their link text, and their targets are never followed. A source change during the run fails attribution and requires a rerun. Summaries use a temporary file and atomic rename, preserving the previous complete observation when a write is interrupted. Logs redact URL values and recognized secret environment values, including JWTs and structured sponsorship authorization keys; summaries omit test arguments, assertion data and failure payloads. Full service/wallet-client JSON is read from a private temporary directory and deleted after summarization. Test fixtures must still avoid logging credentials or passkey assertions in arbitrary formats.

Release steps have a ten-minute default deadline, with twenty minutes for the aggregate service suite and thirty seconds for V6 source preparation and validation; expiry kills the process group, including hung descendants. An output-processing or log-write failure also stops the step. Output is bounded to 32 MiB per step and 1 MiB per line. These local bounds supplement the twenty-five-minute CI job deadline. The required-suite inventory test independently checks all database-bearing files, including ceremony/enrollment persistence, browser enrollment through two HTTP processes, 100-request enrollment races, deployment journal/observations, shared trust policy, typed app grants, canonical authority reconciliation/readiness and genuine signed app requests through two HTTP replicas. It also pins the WebAuthn, signature, Safe profile, onboarding, deployment approval/preflight/observation, Base fee experiment, app authority/dispatch/SmartSession exclusions, canonical authority producer/internal service, local device-probe boundaries, canonical transaction encoding, UserOperation and actual EVM passkey suites. Each required file must appear with nonzero tests and zero skips; adding a required suite means updating the explicit registry and inventory together.

The authority suites separately test deterministic identity/epoch transitions, bounded provider evidence, actual pinned EVM history, PostgreSQL reconciliation and internal orchestration. They include session-administration history alongside account state, prior-anchor rechecks on higher replacement forks, conflict fencing and fresh recovery, 30-second readiness expiry, and live binding checks during app admission. They do not establish a refresh worker, browser session, public login/issuer or live Base provider capacity. The current authority changes have focused observations; a full-gate claim still requires a completed report for the final frozen source.

Use the loop: run the focused test to observe a failure, make the smallest fix, rerun that test, then run the release gate once the related changes are ready. Read the failed step's log and the suite counts instead of treating an exit code alone as evidence. A `running` observation left by a killed process is incomplete, and a successful `preflight` observation only proves prerequisites. A dirty-tree observation is development evidence; rerun against the final commit before making a release claim.

These local checks establish deterministic database and execution behavior. Device interoperability, hosted provider behavior, load, failover and production outcomes require the separate evidence gates in [the implementation strategy](CENTER-WALLET-PLAN.md).
