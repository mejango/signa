The source must remain frozen during a full run. Logs and reports are ignored local artifacts; no secret environment values belong in committed fixtures. Read the failed step, reproduce the failure in its focused suite, fix it, then rerun the affected checks and the integration gate.

A genuine signature over a nested key can survive SDK parsing, reserialization and signer recovery; explicit address/key byte-string checks close that separate boundary. ## Payment and local deployment integration

The signed API now exposes `POST /api/v1/wallet/payment-reviews` and `GET /api/v1/wallet/payment-reviews/:id` for typed app grants only. Legacy owners and bots retain their existing routes. The dedicated wallet origin serves `/wallet/payment?review=<id>` and cookie/CSRF-protected review, approve and cancel routes. Central responses expose the selected credential and exact challenge; owner envelopes are returned only to the original app through signed REST. The fixed callback carries review ID, random app state and issuer, never an assertion or owner signature.

Explicit `wallet.payments` runtime configuration supplies the token and direct V6 terminal. The same private configuration enables the review store and strict operation effect verifier. It is absent by default. The review table retains up to 100,000 total and 128 per-account records, including completed records until bounded cleanup. The ordinary ceremony limits also apply. Neither these bounds nor concurrent correctness tests establish a sustained admission rate.

Initialized local deployment pools now retain immutable environment identity, allocation, spent fees, nonce sequence and settlement anchors. Canonical final settlement charges the complete local cost, checks remaining solvency and releases the lane atomically. Exact replay cannot debit twice or rewrite signed bytes. Actual local tests deploy two distinct wallets sequentially from the original allocation. Unknown complete fees, unexpected nonce, changed finalized history or a restoration fence cannot release capacity. A database cannot independently detect rollback of its own history; production restore provenance remains a separate requirement.
