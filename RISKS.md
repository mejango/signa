# Signa risks and invariants

Signa is a passkey smart-account wallet. Each account is a threshold-one Safe that starts on Base with two owners: the user's passkey signer and a recovery EOA the user holds. Added devices become further full owners. Server keys pay gas and are not meant to own accounts. This file states what the code runs when the runtime is enabled and its lanes are configured (`SIGNA_RUNTIME_ENABLED` defaults to false); whether a deployment has them on is an operating fact this file does not establish. [README.md](README.md) covers configuration.

## Production boundary

- **Only the hosted Base path runs.** `src/index.ts` builds the wallet stack with `createBaseWalletProductionStack` and mounts creation, recovery and device addition only through the hosted Base hosts in `src/rest/wallet/baseHost.ts`. It mounts nothing when the matching `WALLET_CREATION_*` or `WALLET_RECOVERY_*` group is absent, and constructs no account runtime unless `SIGNA_RUNTIME_ENABLED=true`. The Anvil producers exist for tests only.
- **Signup, recovery and device addition start on Base.** The recovery kit declares `network: 'base'` and `chainId: 8453`, and a kit for another network is rejected. Recovery proofs and device additions are anchored to chain 8453. The only other deployment path is the additional-network replay described below, and recovery's swap reaches those networks as described there.
- **Payment reviews are Base USDC only.** The approval-page payment journey recognizes USDC on Base and the JBMultiTerminal that the verified V6 catalog pins for Base. Reviews carry `chainId: 8453`; a request cannot supply the token or terminal. The general plan and user-operation API is wider and keeps its own verification.
- **Execution and recovery state is Signa's own.** Signa does not import Center accounts or credentials and does not serve Center's protocol read routes or MCP.

## Owner state across chains

- **The same address on another network is not the same owner state.** Additional networks (Optimism, Arbitrum and the testnets in `networks.ts`, when `WALLET_NETWORKS_PAYER_KEY` is set) replay the exact Base creation call, which reaches the same CREATE2 address. The account on those chains starts with the owners it was created with. The creation call itself is public: anyone can replay it on a chain where the stack exists, and that copy starts with the original owners too.
- **A new network gets Base's current owners in the same ceremony.** When Base's owners differ from the original pair (after a recovery or a device addition), the quote also returns, for each new network, the Safe owner calls that take the original owners to Base's: swaps first, then additions, then removals (`walletOwnerPlan` in `walletRecoveryReview.ts`). The recovery owner signs them in the browser from the backup file or password with no extra prompt, or with the wallet chosen at signup (once per network); the passkey still approves the deployment once. Before signing, the account page's kit rebuilds the calls from the network's owners and Base's and refuses any other call, so nothing but owner calls on this account, on a chosen network, with a threshold of one, the backup kept, and no owner added on the way that is not in the final set gets signed. The page checks both owner sets against the chains themselves, through each chain's public RPC built into the page (`readChainSafe`; these RPC origins are the only other origins signing pages may connect to), never against the server's word. The target must be exactly Base's owners with a threshold of one, so a server that names an extra or substituted owner gets nothing signed. On a deployed network the starting owners, their order and the Safe nonce must be exactly what that network holds, so no signature can wait for a later nonce and restore an owner after a recovery. A network not deployed yet starts at nonce 0 with the owners its replayed creation call sets up; the page decodes them from that call, which it accepts only because it creates exactly this account's address (CREATE2 over the pinned Safe 1.4.1 proxy) and, with the backup file, because its initializer hash is the one the file recorded. All of an update's owner calls are one Safe transaction at the network's nonce (a delegatecall to the pinned Safe 1.4.1 MultiSend when there is more than one), so nothing is ever signed for a later nonce (`walletOwnerUpdateSafeTx`). The wallet path switches the wallet to each network before it signs. Every passkey owner added is one the account has recorded, with its signer created there first. The update is kept before the deployment is paid for, and a quote whose update failed is never paid. The owner-chains worker then sends that transaction in one bundle. The network is updated only when it holds exactly Base's owners with a threshold of one; until then it reads `updating` and stays blocked like any diverged chain. The worker sends and completes an update only while Base holds exactly the owners it brings, with a threshold of one; a deployment that fails ends its update (`deployment-failed`), as does any later change on Base (`base-changed`). The payment for a new network rechecks Base's owners and its update inside the payer's lock. Only one approved owner change per account and network is on its way at a time (a partial unique index), so two never fund calls for the same Safe nonce.
- **A network add is refused when the backup cannot bring it to Base's owners.** With no original owner left on Base, a replayed creation can never be brought to Base's owners, and quotes are refused with `WALLET_NETWORKS_OWNERS_LOST` ("This account can no longer be opened on new networks."). When the recovery owner is not on Base, the threshold is not one, or Base holds an owner the account has not recorded (an addition mined but not activated), they are refused with `WALLET_NETWORKS_OWNERS_CHANGED`. Owners that change between the quote and its approval stop the payment (`WALLET_NETWORKS_OWNERS_CHANGED`). With no backup file or password given, the account page asks the wallet chosen at signup to sign, and says inline to open the file or password, or this page in that wallet's browser, when neither is there.
- **Adding a device reaches every network the account is deployed on.** The primary passkey approves the same addition for Base and for each other deployed network, one prompt per network, each for that network's own Safe nonce (`deviceChains.ts`). The account page names the networks on one screen before the prompts, rebuilds each SafeTx hash from the account and the device signer it shows before prompting, and keeps the confirmations already given when the browser drops a prompt, for the next tap. The other networks' additions wait until Base shows the device, then go through the owner-chains worker like recovery's swaps. Any approved owner change whose Base change never lands (an abandoned ceremony) is failed after a day (`base-unchanged`), so it stops holding the network. A network whose owners are not the account's recorded owners cannot take the addition; it is reported as failed and stays blocked until updated with the backup. An activated device approves payments with its own passkey.
- **Recovery replaces the passkey on every network the account is deployed on.** One approval signs Base's swap and the same swap for each other deployed network, each for that network's own Safe nonce (`recoveryChains.ts`). A backup file or password signs them all with no extra prompt; a backup wallet asks once per network. Base's swap goes through the recovery relay. The other networks' swaps wait until Base's is on chain, then Center's networks payer pays Relayr to run them, one bundle per family. A network counts as updated only when its own owners show the change and every passkey signer it adds has code there, never on Relayr's word; Relayr runs each call on its own, so a signer whose creation failed gets only its creation sent again. A failed bundle is sent again with the same signed calls, up to three paid bundles per network.
- **The backup signs only a swap the recovery page derived and checked itself.** The page derives the replacement signer from the public key of the passkey it created, using the passkey signer contracts built into its bundle, and keeps that key in the creating browser until every network shows it; a recovery continued in another browser cannot approve. Before the backup signs, the page reads each network's Safe through that network's public RPC at one block and refuses unless the old passkey is a current owner there, the link before it and the Safe nonce match the swap, and every read succeeded. Signa's server cannot name another signer, nonce or owner.
- **A network recovery could not update stays blocked and shown until the backup updates it.** When a network's signed swap no longer fits (its Safe nonce moved), its bundles keep failing, or its owners are not the account's original pair, the recovery page lists it as "Not updated" and the account page as "Needs update". The account page's "Update" sets any network that needs it to Base's owners with the backup, as for a new network. After activation the same recovery page offers a fresh review of only the networks still on the old passkey, signed with the backup again; the review is kept on the server, so a reload resumes it. A network with other owners cannot take this swap and stays blocked. While no networks payer is configured, approved swaps wait rather than fail.
- **Signa reads each chain's owners and compares them with Base's.** `ownerState.ts` reads `getOwners()` and `getThreshold()` on Base and on each deployed chain, each at that chain's head block. A chain is up to date only when it has Base's exact owner set and a threshold of one. A failed or empty read is unknown, never up to date. The last read per chain is stored with its block hash (`rest_wallet_owner_states`) and reused only while that block is still the head, so a new block, a reorg or an owner change reads again.
- **A diverged or unread chain blocks the account's operations there.** Preparing and admitting a passkey account's user operation reads the owners beside the other preparation reads, and refuses with `WALLET_OWNERS_DIVERGED` (409) or `WALLET_OWNERS_UNKNOWN` (503). The account page lists each deployed network as "Up to date", "Needs update" or "Couldn't check". Wallet operations are still Base-only today, so this gate matters once other chains are enabled. Code on a chain proves the account exists there, not that its owners are current. The old passkey can still sign on a diverged chain directly through the EntryPoint or the Safe; Signa only refuses to prepare or relay for it.
- **A kit restores the Base account.** The kit holds the recovery phrase and identity, not the Safe address's state on other chains. Keep the original Safe address with it.

## Approval page

- **The passkey signature is the approval.** The page at `signa.center` shows the review of one Base USDC payment and asks for a passkey assertion with user verification required. The page recomputes the signing digest from the returned operation and refuses a passkey challenge that differs from it. It checks the payment's token and terminal against Base USDC and the V6 JBMultiTerminal written into its own bundle at build time, so a server response cannot name another token or terminal. What it shows is the payment's own calls, decoded from the operation's bytes the way any reviewed call set is (below): the amount, project, beneficiary and spender come from the calldata signed, never from the plan's summary or the stored payment. Base USDC's decimals are known to the page, as to the SDK, so a payment waits for no token read.
- **A review is a fixed operation.** It binds the plan commitment, the operation commitment and hash, the Safe and the app origin and callback. A review is `pending`, `approved` or `cancelled` and has an expiry.
- **Any call set can be reviewed** (`POST /wallet/reviewed-calls`, Base only). Each call is described by the Juicebox SDK (the ABI of the known contract at that address, then a selector lookup across its ABIs), else by the Etherscan-verified ABI of its target, read by Signa with `SIGNA_ETHERSCAN_API_KEY` (for an EIP-1967 or transparent proxy, the implementation's ABI, from the implementation slot read at that moment), else shown as raw calldata with a warning. Every call is labeled by its source, and every warning is on the page before the one passkey prompt. A failed lookup (no key, Etherscan unreachable or rate-limited) is shown raw with "Couldn't look up this contract." and is never decoded or cached.
- **The page decodes the bytes itself.** It checks every call against the operation's calldata and decodes each one with the function its source names: the one function of the stored Etherscan ABI, or the one the SDK matched. A decode counts only when the arguments re-encode to the exact calldata, so a tampered ABI can at most rename parameters. The SDK stays off the page: contract names, the names of known addresses and warnings come from the server's SDK model, the arguments shown come from the page's own decode. A payment's approve and pay are decoded with the page's own functions, so their parameter names are fixed too.
- **Etherscan ABIs are not reviewed by Juicebox.** Their parameter names are the contract publisher's. A proxy admin can change the implementation after the review, or after signing and before inclusion; the review shows the implementation it read, and the signed bytes stay the same.
- **Token amounts format with decimals the approval page reads itself.** The page finds a call's token and amount by its exact signature (the SDK's rule, held to it by a parity test) and reads `decimals()` and `symbol()` from Base's public RPC; approval waits for the read. A failed read, or an unreadable symbol, shows base units with a warning. A token's own symbol is its publisher's; the token address stays on the page.
- **Self-administration and delegatecall are refused.** Any call to the account itself, whatever its selector, and any ERC-7579 or Safe execution with a delegatecall operation, is refused from the raw call before any decode or lookup, by the server and again by the page. Owners and modules change only through Signa's own recovery and device ceremonies. Owner actions on other contracts (rulesets, splits, permissions, ownership) are allowed with the SDK's warnings listed first.
- **A reviewed call set is verified whole.** It is verified only on a canonical successful execution of exactly its calls; an inner revert is failed and a reorg unknown. Nothing is claimed about what the calls did.
- **The page runs inside app frames and popups.** Only origins in `WALLET_FRAMEABLE_APP_ORIGINS` may frame it. Assertions and CSRF values stay in page memory and are not stored.
- **Pages that sign frame no other origin.** The account, payment, signup, recovery and device pages send no `frame-src` and grant the Payment Request API to no one, so no third-party frame sits beside a passkey prompt. Coinbase's Apple Pay frame lives only on the funds page, whose `Permissions-Policy` turns passkeys off.

## Gas sponsorship

- **Pimlico is the paymaster for now.** Wallet user operations use the ERC-4337 paymaster and bundler configured in `REST_ERC4337_CONFIG` under a hosted Pimlico sponsorship policy. Signa signs no paymaster data itself.
- **Signa caps sponsored gas per account, per chain, per rolling day** (`SIGNA_SPONSOR_ACCOUNT_DAILY_WEI_<chainId>`, required for every chain with a Pimlico policy). Prepare reserves the operation's maximum gas cost before asking Pimlico, replaces it with the canonical `actualGasCost` once that execution reaches its confirmation depth, and releases it only when the operation is retired unsent, proven expired, or never signed before its review expired. An unknown submission keeps its reservation. A retired approval's signed bytes stay with its app until the chain settles them; if the app sent them to Pimlico itself, that one operation's gas would go unmetered (Pimlico's own policy still bounds it). The window rolls from preparation, so spend can run a few minutes past a day's cap at the window's edge. The cap is per Signa account: a person with many accounts gets one cap each, and Pimlico's own sponsor policy remains the overall limit.
- **Over the cap, or when Pimlico refuses, the account pays.** The payer is fixed at preparation (`paymasterAndData` is signed), and the one approval shows it: "Gas: sponsored" or "Gas: up to <amount> ETH from your account". A Safe without that much ETH sees "Needs ETH for gas on <chain>." and cannot approve. Session operations and chains configured with `requirePaymaster` are refused instead of becoming Safe-paid.
- **Own sponsor lanes are deferred.** `REST_ERC4337_SPONSOR_ROUTES` can select separately budgeted policies by server-issued voucher, but Signa runs no paymaster of its own. That waits for the move off Railway to GCP and KMS.
- A signed sponsored operation can stay executable until its paymaster window ends. Signa releases its nonce reservation on a canonical revert or proven expiry, and then fences the wallet to that exact nonce until the chain settles it.

## Server keys

- **Server keys pay gas only.** `WALLET_CREATION_SIGNER_KEY` pays Safe creation, `WALLET_RECOVERY_SIGNER_KEY` pays recovery and device-addition transactions, and `WALLET_NETWORKS_PAYER_KEY` funds additional-network bundles, including recovery's swaps on those networks. None of them signs for a Safe or approves a payment. Ownership is not enforced by the code: creation checks that the recovery owner is code-free but not that it differs from a server key, so an operator must never use a user's recovery EOA as a server key.
- **Keep the lanes separate.** Use a different key for each lane; the sender nonce and spend accounting are per lane. Startup does not compare the keys. Recovery and device lane initialization refuses a sender that already appears in the deployment pools, which catches reuse of the creation key only after the fact.
- **Keys sit in the hosting environment today.** The Railway service holds them as environment variables. Moving them to KMS is part of the planned move to GCP.
- Bounds: creation checks a reviewed allocation and initial nonce at startup and fences the pool as `allocation-exceeded` if a finalized debit exceeds it; recovery is bounded by `WALLET_RECOVERY_MAX_OPERATIONS` and `WALLET_RECOVERY_MAX_COST_WEI`; its swaps on other networks by three paid bundles per network, each within the networks payment cap.

## Priority risks

- **Gateway custody is pending until its outcome is proved.** `JBRouterTerminalGateway_QueuePendingCall` records retained input. A successful retry transaction can record another failure and leave custody pending. Establish settlement from `JBRouterTerminalGateway_ProcessPendingCall`, or an accounted refund from `JBRouterTerminalGateway_RefundPendingCall`, with the correct emitter, ID and arguments. `pendingCallCount` counts issued IDs; a zero commitment does not distinguish settlement, refund and an ID that never existed. Refunded fees do not restore core `feeFreeSurplusOf`.
- **Receipt outcomes depend on the deployed generation.** Recognize buyback sell failures from every recorded current and retired hook; an outer cash-out receipt can succeed while project tokens are returned. A routed payment's terminal event names the immediate forwarding contract as payer, so bind its emitter, caller, project and beneficiary to the reviewed route. Arbitrary emitters cannot establish settlement.
- **Previews depend on the selected implementation and observed state.** Buyback 1.4.0 pay metadata contains `(amountToSwapWith, minimumSwapAmountOut, skipSplits)` under the resolved hook's metadata ID. Pool availability, rulesets and hook configuration can change before execution. Preserve the actual outer terminal for approvals and payment bytes.
- **Unavailable observations remain unknown.** The account page's balance total counts a failed chain read as zero (`balances.ts`), although each chain's value stays unknown; read the per-chain values. RPC failures, missing deployments, failed previews and unavailable indexer state cannot establish zero balances, permission, settlement or a usable route. A signed operation with an unreadable sponsor window holds its wallet to its nonce until settlement evidence exists. Preserve chain, version, project, token, currency, decimals and integer strings; verify current financial state at a canonical block hash.
- **Reverted and submitted operations stay live.** A reverted EntryPoint `handleOps` rolls back nonce increments, but the signed bytes remain executable until their deadline. Signa releases the reservation on a canonical whole-bundle revert or proven expiry and keeps the wallet fenced to that nonce until settlement.
- **Existing authorization boundaries remain necessary.** Reviewed operations are immutable; execution progress is tracked separately. API read, plan and relay grants are separate from onchain authority. Fund movement through the approval page requires a fresh passkey approval. The general operation verifier also accepts the recovery EOA as a threshold-one owner signature, and an explicitly installed session acts within its limits.
- **Source references have explicit trust assumptions.** Protocol sources keep their reviewed revisions and hashes. Package versions and ABI decoding alone do not prove deployed bytecode. The wallet client for apps is `@me.jango/signa`; its sign-in code and Signa's page must agree on the protocol strings.

## Invariants to Verify

- No path outside the hosted Base hosts creates, recovers or adds a device to a production account.
- A payment review's token, terminal, chain and Safe come from host configuration and the verified catalog, never from a request.
- The passkey challenge equals the digest recomputed from the reviewed operation.
- A server key never signs on behalf of a Safe owner. Operators keep one key per lane.
- Pending custody, retry failure, settlement and refund remain distinct outcomes backed by canonical event evidence.
- Payment metadata, output floors, recipients, calldata and value match the exact reviewed operation; unsupported settlement formats fail closed.
- Every privileged request retains its authorization, replay, expiry and scope checks; read capabilities do not confer wallet authority.
- A failed read never becomes success or permission, and only the balance total described above treats it as zero.

Run `npm run check` for the release gate.
